## Findings

1. **[blocker] `src/habits/storage/repository.py:103` — A check-in can survive its caller’s rollback.** With the SQLite configuration in `src/habits/storage/db.py:9`, the preceding `SELECT` statements do not start a database transaction under sqlite3’s legacy transaction mode. If the savepoint is the first transaction opened, releasing it commits the insert. Ensure a real outer transaction owns the savepoint. Add a storage test that creates and commits a habit, adds a check-in in a fresh session, rolls back, and verifies from another session that the check-in is absent. The existing storage tests create the habit in the same transaction, which masks the bug.

2. **[blocker] `src/habits/core/services.py:38` — Archiving or deleting a habit can race with check-in creation.** An archive can commit after `get_habit` reads the active habit and before `add_checkin` inserts. A delete in the same interval causes a foreign-key violation, which `src/habits/storage/repository.py:106` reports as `409 checkin_exists` even when the habit and check-in are both absent. Make the write conditional on the parent still existing and being active, and translate only the habit/day unique conflict to `CheckInExists`. Add two-session tests that force each parent change between the read and insert and assert `409 habit_archived` or `404 habit_not_found`, respectively. `test_duplicate_checkin_conflict` exercises two creators only.

3. **[blocker] `src/habits/api/routes/checkins.py:46` and `:62` — Query and path dates accept timestamps.** The POST body enforces `YYYY-MM-DD`, but `start`, `end`, and DELETE’s `day` use Pydantic’s coercive `date` parser. For example, `DELETE /habits/1/checkins/1768435200` can delete the January 15, 2026 check-in. The contract requires a full-date string. Share the body’s date-format validation across all three parameters. Test that numeric timestamps and midnight datetime strings return `422 validation_error`, and that a rejected DELETE preserves the row.

4. **[blocker] `src/habits/api/routes/checkins.py:34` — A JSON `null` request can create a check-in.** The contract permits an omitted body, `{}`, and `{"day": null}`. A supplied body must be a `CheckInCreate` object. The optional body annotation also accepts the literal JSON document `null` and defaults it to today. Distinguish an absent body from explicit JSON `null`. Test the latter with `Content-Type: application/json` and assert `422 validation_error` and no new row.

5. **[minor] `src/habits/api/deps.py:35` — The default day and creation timestamp come from separate clock reads.** A POST spanning local midnight can record the previous day with a creation timestamp on the next local day. Derive `today` from the same request-scoped instant used for `created_at`. Add an HTTP test that sets `HABITS_TIMEZONE`, fixes only the UTC instant near midnight, and asserts both the default check-in day and stats `as_of`. The current fixture overrides `get_today` itself, so it would also miss a regression that always uses the UTC date.
