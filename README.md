# AI Project Blueprint

A repository skeleton for solo projects built by several AI agents: a strong **architect** that plans and slices work, small **local executors** that write code, a **reviewer** from a different model family, and later a **tester**. Agents coordinate through files in `work/`, so any tool works: Claude Code, Codex CLI, Gemini/Antigravity CLI, Aider.

> Replace this README with your project's own once you start; keep links to the two docs below.
> Process: [docs/human/workflow.md](docs/human/workflow.md) · Settings: [docs/human/configuration.md](docs/human/configuration.md)

## What's inside
```
AGENTS.md                 ≤150 lines, the ONLY always-loaded instruction file (human-owned)
CLAUDE.md                 2-line shim: @AGENTS.md (+ tiny Claude-only notes)
.gemini/settings.json     makes Gemini CLI read AGENTS.md
.agents/
  config.json             THE settings file: models, tiers, budgets, reviewer, gates, protected/lock paths
  roles/                  architect, executor-local, reviewer, tester, explorer prompts
  skills/                 SKILL.md procedures: slice-tickets, review-ticket, update-docs, write-adr
  profiles/               stack add-ons: python, rust, unity, unreal, web-design-system
.claude/                  Claude Code: settings + hooks, subagents (executor-* generated by sync.py)
docs/
  ai/                     FOR AGENTS: INDEX router, modules.yaml, contracts/, conventions, gotchas, glossary
  architecture/           diagrams shared by both doc sets (Mermaid + YAML)
  human/                  FOR YOU: overview, architecture narrative, how-to-run, changelog, workflow
  adr/                    decision records
  plan/                   vision, milestones, initial-overview (frozen Phase 0 snapshot), all written by human + architect
work/
  STATE.md                status board (auto-generated part + architect's next action), read first
  tickets/  reviews/      coordination bus (committed)
  templates/              ticket, ticket.example, batch (many tickets in one file), review
  archive/                done tickets (hidden from agents)
scripts/agent/            stdlib-only Python tools (Windows / Linux / macOS)
```

## Setup (once per project)
1. Copy this folder to a new repo. `git init`, commit on `main`.
2. Delete the profiles you don't use in `.agents/profiles/` and their lines in `AGENTS.md`. Delete `docs/architecture/game/` for non-games.
3. Add your stack's ignores to `.gitignore` (listed at the bottom of each profile).
4. Install: Python ≥3.10 (scripts use only the standard library), Claude Code, Codex CLI (`codex login` once).
5. Pick models, tiers and budgets in **`.agents/config.json`**. All the knobs are explained in
   [docs/human/configuration.md](docs/human/configuration.md). Defaults: architect Opus, executors Sonnet (Opus for tier L), reviewer Codex.
6. `python scripts/agent/sync.py` applies the config to Claude Code. It writes the model, generates the executor subagents and copies the skills. Re-run it after every config edit.
7. Start Claude Code in the repo, set effort to high, and say: *"You are the architect. Start Phase 0."*
   During Phase 0 the architect proposes the stack-specific settings (gate commands, the commands headless workers may
   run, lock files) and asks whether to calibrate on the first loop run. You apply them with one command:
   `python scripts/agent/config_apply.py`.

Optional local executor (Aider + Qwen): see `executor._local_tier_example` in the config and the configuration doc.

## What happens after Phase 0
A script runs the ticket loop; the architect only plans, unblocks and reviews the whole milestone.
Process diagram: [docs/human/workflow.md](docs/human/workflow.md).

| Step | Who | What runs |
|---|---|---|
| 0. Foundation | you + architect (Opus) | `docs/plan/*`, `modules.yaml`, contracts, ADRs. It proposes `AGENTS.md` Commands, `verify.commands` and `verify.fix_commands`, and you apply them. Ends with `docs/plan/initial-overview.md`, which you approve and freeze |
| 1. Slice | architect, one session | `milestone.py start M1`, then all milestone tickets in one batch file → `ticket.py new-batch <file> --milestone M1 --ready`. Each ticket owns the test file that proves it (tests first) |
| 2. Loop | **`run_loop.py M1`** (no LLM orchestrating) | for each runnable ticket, 2 conflict-free tickets at a time: headless Sonnet worker (`claude -p`) started inside `.worktrees/<id>` → tests committed first and proven failing (`--red`) → implementation → auto-format → gates → Codex review (read-only; S/M on the fast model, L on the strongest) → fix rounds (max 3) → merge into `int/M1` → dependents start |
| 3. Unblock | architect, new short session | only the tickets listed under "Needs architect" in `work/STATE.md`; then rerun `run_loop.py` |
| 4. Milestone end | architect (+ tester), one session | whole-milestone review, drift check, `doc_fresh.py`, skill `update-docs`, changelog, usage table (`usage.py --milestone M1 --write`), one PR per milestone, stacked: `main ← int/M1 ← int/M2 ← …`; the next milestone starts at once from `int/M1` |
| 5. PR | **you** | review and merge bottom-up (merge commits keep the stack intact). Then `ticket.py status <ids> done`, `ticket.py archive --done --remove-worktrees`, `milestone.py restack M1` |

`run_loop.py` exit codes: 0 done · 2 needs architect · 5 usage limit hit (rerun later; it resumes).
With calibration on, the first run of a milestone stops after N tickets and prints a report.
Useful anytime: `ticket.py list`, `state.py`, `usage.py`, `pack.py T-id` (exactly what a model gets), `run_review.py T-id --dry-run`, `sync.py --check`.

## Token rules built into the template
| Item | Rule |
|---|---|
| architect | out of the ticket loop; one short session per job; batch writes (biggest saving) |
| `AGENTS.md` | ≤150 lines, non-obvious rules only |
| worker | pack sent on stdin (no extra reads), tells it not to re-read files; `--max-turns` per tier |
| executor context pack | tier `pack_tokens` (S 24k, M 40k, L 60k), enforced by `pack.py` |
| ticket | tier `max_files_owned`, ≤7 steps, body ≤1,500 tokens (`ticket_lint.py`) |
| reviewer | read-only, whole packet in the prompt, medium effort (high on last round), re-reviews see only new changes, lock/generated files listed with line counts but no content, diff capped at 600 lines |
| lock/generated files | names only, never content: in packs, review packets and the Read hook (`generated_globs`) |
| formatting | `verify.fix_commands` run before the gates, so a formatting slip never costs a worker run |
| gate output fed back | last 40 lines |
| loop output | one line per step; full logs in `work/.pack/` |
| docs | loaded on demand through `docs/ai/INDEX.md` |

## Rules you should keep
- **You approve `AGENTS.md`, `docs/ai/conventions.md` and `.agents/profiles/*` line by line.** Agents write everything else. A 2026 study found LLM-written instruction files raised cost and lowered success.
- **Gates before reviews.** The reviewer never sees a ticket whose build, tests or file-ownership check failed.
- **Reviewer ≠ executor model family.**
- **Calibrate first.** Keep `loop.calibration` on for the first milestone. `loop.max_parallel` is 2: only tickets with disjoint files and locks run side by side, each in its own worktree. Parallel workers save time, not tokens; use 1 for a single-GPU local tier.
- **Local models (if you add an `aider` tier): one GPU = one executor at a time.**

## Windows notes
- Run scripts with `python` from PowerShell or Git Bash; WSL2 works too. Unity/Unreal editors stay on Windows.
- No symlinks needed: `CLAUDE.md` imports `AGENTS.md`, skills are copied by `sync.py`.
- Claude Code hooks call `python`; make sure it is on PATH.

## Verify before relying on it
Tool details change fast. As of Nov 2026: Claude Code reads `AGENTS.md` natively (v2.1.277+) but ignores it when a `CLAUDE.md` exists, so this template uses the import shim; Codex truncates instruction files above 32 KiB; Gemini CLI needs `context.fileName` (done in `.gemini/settings.json`); the reviewer command uses `codex exec --sandbox read-only -c model_reasoning_effort=… --output-last-message <file> -` (prompt on stdin), and the worker uses `claude -p --model … --effort … --max-turns … --output-format json --permission-mode acceptEdits --allowedTools …`; check these flags on your versions. Re-check when you set up.
